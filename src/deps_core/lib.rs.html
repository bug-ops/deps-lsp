1// This crate defines the `Registry`/`Ecosystem` boxed-future trait signatures (and the
2// `impl_dependency!`/`impl_version!` macros generating their `Send`-bound futures) that every
3// ecosystem crate's `get_latest_matching`-style implementation coerces into; rustc's default
4// recursion limit has proven occasionally insufficient to prove that bound for several such
5// implementations, downgrading a previously-silent trait-solver retry into
6// `recursion_depth_exceeding_limit`, which the fuzz CI job's `-D warnings` nightly build turns
7// into a hard error (rust-lang/rust#159228). Same class of fix as deps-cargo (#745),
8// deps-nuget (#696), deps-swift (#673), deps-composer.
9#![recursion_limit = "256"]

11//! Core abstractions for deps-lsp.
12//!
13//! This crate provides the foundational traits and utilities used across
14//! all ecosystem-specific implementations (Cargo, npm, PyPI, etc.).
15//!
16//! # Architecture
17//!
18//! deps-core defines:
19//! - **Traits**: `Registry`, `Version`, `Metadata`, `Ecosystem`, `ParseResult`
20//! - **HTTP Cache**: Shared caching layer with ETag/Last-Modified validation
21//! - **Error Types**: Unified error handling across all ecosystems
22//!
23//! # API stability (issue #769)
24//!
25//! Most public structs and enums here are `#[non_exhaustive]` so a new field or variant
26//! never breaks a downstream ecosystem crate's exhaustive match or struct literal. This is a
27//! per-kind decision, not one policy for both: on a **struct** with no `pub` fields,
28//! `#[non_exhaustive]` is a semantic no-op (an external crate can't literal-construct or
29//! destructure it either way), so such structs are deliberately left exhaustive instead. On
30//! an **enum**, `#[non_exhaustive]` always forces a downstream `match` to carry a wildcard
31//! arm, regardless of any variant's field visibility — each enum opts in when that forced
32//! wildcard is wanted and stays exhaustive when a future variant should instead be a
33//! compile error downstream; see the individual enum's own doc comment for which applies.
34//!
35//! A few pre-1.0 dependency types remain visible in public signatures as a deliberate
36//! semver commitment rather than an oversight:
37//! - [`error::SanitizedRegistryError`] implements `From<reqwest::Error>` — a `reqwest`
38//!   major bump that reshapes `Error` is a breaking change for this crate too.
39//! - [`parser::yaml_scalar_string`] takes `&yaml_rust2::Yaml`; `yaml_rust2` is re-exported
40//!   from the crate root so callers can name the type without their own direct dependency,
41//!   and a `yaml-rust2` major bump is likewise a breaking change here.
42//! - `deps-gitlab-ci`'s `gitlab_version_req` (`crates/deps-gitlab-ci/src/component.rs`)
43//!   returns `semver::VersionReq` directly — low risk since `semver` is unusually stable
44//!   pre-1.0, but the same commitment applies.
45//!
46//! ## LSP type stability (issue #832)
47//!
48//! The `Ecosystem`, `Dependency`, `ParseResult`, and `EcosystemFormatter` trait signatures
49//! — and the public `lsp_helpers` / `completion` helper functions — are typed directly
50//! against `tower_lsp_server::ls_types` types (`Hover`, `Diagnostic`, `CodeAction`, and so
51//! on). `tower-lsp-server` is pinned pre-1.0, so a `tower-lsp-server` minor bump (e.g. 0.23
52//! → 0.24) is not an implementation detail this crate can absorb silently — it forces a
53//! breaking release of `deps-core`: a minor version bump while `deps-core` itself remains
54//! pre-1.0, a major version bump once `deps-core` reaches 1.0.
55//!
56//! Downstream consumers implementing [`ecosystem::Ecosystem`] should depend on the exact
57//! matching `tower-lsp-server` version through the [`tower_lsp_server`] re-export rather than
58//! adding their own separate direct dependency, which could otherwise drift out of sync with
59//! the version `deps-core` was built against.
60
